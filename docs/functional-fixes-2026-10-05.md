## 并发与资源约定

- 停止路径不在持 p->lock 时获取 wait_lock。通知与 STOPPED 发布受等待协议保护，父进程不会因“检查后才停止”而永久睡眠。
- 管道阻塞读写在不持管道锁时处理默认停止/继续，恢复后继续未完成的 I/O；其他可投递信号仍经用户陷阱处理，阻塞读可返回 -1、部分写可返回已传输字节数。投递信号也取消已登记但尚未真正睡眠的等待。Shell 的管道/命令序列在等待被信号打断时继续回收已知子进程，不因多次 SIGCONT 提前退出。
- 交接锁时重新检查已到达的 SIGCONT、SIGKILL 或 kill 标志，避免继续/终止唤醒先到却随后再次进入 STOPPED。
- Shell 追踪解析时的全部分配，包含尚未连接到完整语法树的节点。解析失败与 fork 失败释放分配并返回主循环；fork 成功后父进程释放自己的树，子进程继续使用 COW 副本。
- 每行最多 99 字符，解析分配表最多 100 个节点；达到上限或分配失败报告错误。原输入长度、参数数量和作业表上限不增加。
- O_APPEND 是打开文件描述符的属性，dup/fork 共享同一 file 时保留；只影响普通文件写入，不改变读取偏移规则、权限检查或 mmap 语义。
- EOF 选择和 writei 在同一 inode 锁内执行；独立 fd 并发追加不覆盖。大写入仍按日志容量分块，允许在块之间交错，不提供整次大 write 的原子保证。
- 不改变系统调用编号、磁盘结构或 44 个预置程序清单。

## 开发与测试记录

原版本在两种 CPU 配置均复现四项缺陷；旧 Shell 内存测量为 84 → 276 KiB，`>>` 的错误内容为 `xy\ndef\n`。既有标准测试全部通过，说明仅重复旧测试不能发现这些路径。

新终端测试进一步发现原管道阻塞循环不检查待投递信号，以及 Shell 内部 wait 被 SIGCONT 打断后可能提前结束管道组长。已补齐阻塞管道读/写停止恢复和 Shell 已知子进程等待。

测试开发时也发现宿主脚本时序假设不成立：后台 top 会在提示符之后继续输出；组信号按成员投递，Shell 收到组长停止事件时其他成员可能尚未停止。脚本改为检测本次操作后的提示符，并在有界时间内检查整个组停止，没有降低停止、恢复、退出和后台存活要求。初版脚本失败日志保留在本地 test-results。三核串口可在一行输出尚未结束时插入控制字符回显，因此测试等待完整输出行后再发送终端信号。

新增验证入口：

```sh
python3 test-shell.py --cpus 1
python3 test-shell.py --cpus 3
# 独立复现某一项：--case syntax / memory / append / jobs
```

脚本每项重建 fs.img，不可与同 checkout 的其他 QEMU 测试并发。保存串口、操作记录、CPU 配置、Git 基线、工作区状态及 JSON 汇总。`test-shell.py` 已加入 CI 和 AGENTS.md 的完整验证链。
